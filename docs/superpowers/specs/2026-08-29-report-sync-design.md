# Синхронизация отчёта с локальным файлом — дизайн

Дата: 2026-08-29
Статус: approved (по диалогу brainstorm)

## Objective

Внутри каждого отчёта появляется кнопка **«Синхронизация»**: она сохраняет данные отчёта в
локальный JSON-файл на телефоне и держит этот файл в актуальном состоянии. При нажатии
приложение сравнивает текущие записи отчёта с последней синхронизированной копией:

- изменений нет (точная копия) → сообщение «Актуализация не нужна»;
- добавлены только новые строки → файл обновляется автоматически;
- старые записи изменены или удалены → запрос подтверждения: заменить ли старые записи
  в файле текущими. «Да» — файл заменяется, «Нет» — файл и данные приложения не меняются.

Это **не бэкап** (бэкап — это все отчёты разом). Файл синхронизации описывает **один отчёт**.
Синхронизация односторонняя: веб → файл. В приложение из файла ничего не импортируется
(«в вебе ничего не скидывается»).

## Scope

### Included
- Кнопка «Синхронизация» в `ReportScreen` (рядом с «Напоминание»).
- Таблица `syncs` в Dexie (v2) — слепок последней синхронизации на отчёт.
- Чистая diff-логика в `src/logic/sync.ts` + полное тестовое покрытие.
- Сохранение JSON-файла отчёта на телефон при создании и каждом обновлении.
- Сообщения о результате синхронизации.

### Excluded
- Импорт из файла обратно в приложение.
- Автосинхронизация (по таймеру/фону) — только по нажатию кнопки.
- Синхронизация настроек, напоминаний, полей как критерий diff.
- Изменение существующего бэкапа (Экспорт/Импорт) — не трогаем.

## Техническое ограничение (обоснование подхода)

iOS Safari не даёт веб-приложению постоянный дескриптор файла из «Файлов» (File System Access
API недоступен). Поэтому выбран подход «внутренний слепок + пересохранение файла»:

- приложение хранит в IndexedDB копию последнего синхронизированного состояния отчёта —
  это и есть «то, что в файле»;
- при каждом обновлении содержимого приложение заново сохраняет JSON на телефон
  (Web Share API → «Сохранить в Файлы»; на десктопе — обычное скачивание).

Файл выбирается/сохраняется пользователем один раз при создании синхронизации; дальше
выбор не требуется (единственное действие при будущих обновлениях — подтвердить сохранение
в штатном диалоге iOS).

## Формат файла

Имя: `<имя-отчёта>-sync.json` (небезопасные для имени символы заменяются на `_`).

```json
{
  "version": 1,
  "reportId": "rep-...",
  "reportName": "Давление",
  "syncedAt": "2026-08-29T10:00:00.000Z",
  "fields": [{ "id": "fld-...", "name": "ВД / НД / П", "type": "text", "required": false, "width": 30 }],
  "entries": [{ "id": "ent-...", "reportId": "rep-...", "values": { "fld-...": "120/80" }, "createdAt": 123 }]
}
```

`version: 1` — версия формата. `syncedAt` — время последней записи файла (ISO-строка;
в БД слепок хранит `syncedAt: number` в миллисекундах, при сборке файла конвертируется
в ISO через `toISOString()`).
Критерий diff — **только записи** (`entries`). Поля и имя отчёта пишутся в файл как контекст
и подтягиваются при каждой перезаписи.

## Модель данных (IndexedDB)

Dexie-схема переезжает на версию 2, добавляется таблица:

```
syncs: 'reportId'
```

Строка: `SyncState { reportId, reportName, fields: Field[], entries: Entry[], syncedAt: number }`.
API в `src/db/db.ts`:

- `getSyncState(reportId): Promise<SyncState | undefined>`
- `putSyncState(state: SyncState): Promise<void>`
- `deleteSyncState(reportId): Promise<void>` (при удалении отчёта — каскад, вместе с `deleteReport`)

## Diff-логика (`src/logic/sync.ts`, чистая, без DOM)

```ts
type SyncOutcome =
  | { kind: 'identical' }
  | { kind: 'append-only'; added: Entry[] }
  | { kind: 'conflict'; added: Entry[]; modified: Entry[]; deleted: Entry[] };

function classifySync(current: Entry[], synced: Entry[] | undefined): SyncOutcome
```

Сравнение по `id` и по `values` (deep equal). `createdAt` в diff не участвует (при
редактировании записи не меняется).

- `synced === undefined` (первая синхронизация) → всё множество текущих записей считается
  `added` → outcome `append-only` (создание файла без вопросов).
- id-множества и значения совпадают → `identical`.
- есть только новые id (`added`), нет изменённых и удалённых → `append-only`.
- есть изменённые значения (общие id) или удалённые id → `conflict`
  (независимо от наличия добавлений).

Сборка файла:

```ts
function buildSyncJson(report: Report, entries: Entry[], syncedAtMs: number): string
```

- возвращает отформатированный JSON (формат выше, `version: 1`);
- имя файла — `syncFilename(reportName: string): string`.

## UI-поток (`ReportScreen`)

Кнопка «Синхронизация» (`class="no-print"`) в ряду кнопок отчёта. При нажатии:

1. `entries = await listEntries(reportId)`, `synced = await getSyncState(reportId)`.
2. `classifySync(entries, synced?.entries)`:
   - **identical** → inline-сообщение «Актуализация не нужна».
   - **append-only** → `putSyncState({ ...текущие данные, syncedAt: now })`,
     сохранить файл на телефон, сообщение «Синхронизировано: добавлено N записей
     (файл обновлён)». Для первой синхронизации: «Синхронизация создана (N записей)».
   - **conflict** → `window.confirm('В файле синхронизации есть записи, которые были
     изменены или удалены. Заменить их текущими данными отчёта?')`:
     - «Да» → `putSyncState(...)`, сохранить файл, сообщение «Файл обновлён».
     - «Нет» → ничего не менять, сообщение «Файл не изменён».
3. Сообщения — inline под кнопкой (паттерн `MoreTab`), а не `alert`.

Сохранение файла — утилита `saveSyncFile(report, entries)`:

- iOS/совместимые: `navigator.share({ files: [new File([json], name, {type:'application/json'})] })`
  (имеется `navigator.canShare`-гард);
- fallback: Blob + `<a download>` (как в `MoreTab.exportBackup`).

## Обработка ошибок

- `navigator.share` отклонён пользователем (AbortError) → молча игнорируем, слепок уже
  сохранён — при следующем нажатии «Синхронизация» покажет «не нужна» либо пересохранит.
- Ошибки IndexedDB → сообщение «Не удалось выполнить синхронизацию. Попробуйте ещё раз».

## Тестирование

### `src/logic/sync.test.ts` (чистая логика)
1. identical: те же id и values.
2. append-only: только новые id (1 новая строка; несколько).
3. conflict — изменённые: общий id, другие values.
4. conflict — удалённые: id есть в слепке, нет в текущих.
5. conflict — новые + изменённые одновременно.
6. первая синхронизация (`synced === undefined`): все записи = added, outcome append-only.
7. пустой отчёт / пустой слепок → identical.
8. порядок записей не влияет на классификацию.
9. `buildSyncJson`: валидный JSON, поля version/reportId/reportName/fields/entries/syncedAt.
10. `syncFilename`: небезопасные символы → `_`, расширение `.json`.

### `src/db/db.test.ts` (дополнения)
- `putSyncState`/`getSyncState` round-trip; `deleteSyncState` удаляет.
- `deleteReport` каскадно удаляет слепок синхронизации.

### `src/components/ReportScreen.test.tsx` (UI)
- Первая синхронизация: нажатие → `db.syncs` получил слепок, файл «сохранён»
  (мок `navigator.share` или `<a>`-клик как в `MoreTab.test`), сообщение
  «Синхронизация создана».
- append-only: добавлена запись после синка → нажатие обновляет слепок, сообщение
  «добавлено N».
- identical: нажатие → сообщение «Актуализация не нужна», `db.syncs` не изменён.
- conflict + «Да»: `confirm` → true, слепок заменён, файл пересохранён.
- conflict + «Нет»: `confirm` → false, слепок и файл не тронуты, сообщение «Файл не изменён».

Все UI-тесты — на реальных `db` (fake-indexeddb) с `beforeEach` reset, как в существующих.

## Assumptions / решения

- Дифф только по записям; изменённые поля отчёта (добавление колонки) не считаются
  конфликтом — при перезаписи файла поля просто обновляются.
- Первая синхронизация существующего отчёта с записями — автосоздание файла без
  подтверждения (это и есть «создание синхронизации»).
- Файл — зеркало данных приложения на момент синка; ручная правка файла пользователем
  не отслеживается (нет чтения файла).
- Кнопка «Синхронизация» — один раз на отчёт; отдельной функции «удалить синхронизацию»
  в этом инкременте нет (YAGNI; при удалении отчёта слепок удаляется каскадом).
